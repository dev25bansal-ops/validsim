# 🧩 Module Specs

Five core modules of [[Solution Architecture]], each with its sprint week from [[8-Week Sprint Plan]].

> [!important] Blueprint status — 2026-09-21
> This is the intended module boundary, not a shipped-service inventory. The repository currently implements the shared Python engine, FastAPI/Typer adapters, memory/Redis jobs, SQLite/PostgreSQL stores, static dashboard, PDF/Markdown/HTML reports, and local composite Actions. gRPC/Protobuf, RabbitMQ, Kubernetes/Argo, Isaac execution, cloud object recording, and hash-chained compliance storage are planned/not implemented.

## Module 1 · Ingestion & Orchestration *(Sprint W1–W2, W6)*

| Component | Technology | Specification |
|---|---|---|
| API Gateway | FastAPI (Python 3.10+) | **Shipped** — async REST, OpenAPI, optional process-local write rate limiting |
| gRPC Service | Protocol Buffers | **Planned** internal RPC; not implemented |
| Job Queue | Memory / Redis 7.x; RabbitMQ planned | **Shipped** FIFO queue with depth cap; no priority or dead-letter queue |
| Orchestration | Docker Compose now; Kubernetes 1.29+ planned | No GPU node autoscaling today |
| Workflow Engine | Argo Workflows | **Planned** DAG execution; not implemented |
| Config Parser | Pydantic v2 | Task library, robot spec, environment validation |
| Model Format Support | PyTorch, ONNX, TensorRT | Checkpoint ingestion |

> [!note] ONNX/PyTorch/TensorRT flexibility is the hedge against Risk #4 ("VLA architectures change rapidly", [[Risk Register]]) — evaluation is abstracted from model architecture.

## Module 3 · Adversarial Scenario Generator *(Sprint W4)*

> [!warning] What ships is the rule-based generator, not the LLM one
> The **12-category taxonomy and the `AdversarialScenario` model ship today**,
> generated by a deterministic, seeded rule-based generator
> (`validsim/scenarios/generator.py`) — reproducible from
> `(checkpoint_id, task_id)`, air-gapped, no network I/O.
>
> An LLM backend also exists (`validsim/scenarios/llm_generator.py`:
> `LLMScenarioGenerator`, OpenAI-compatible provider, strict schema validation,
> deterministic fallback, category top-up, plus the env-driven factory
> `create_scenario_generator()`). It is **implemented and tested but not
> reachable from a run**: `validsim/engine/pipeline.py:131` hardcodes
> `ScenarioGenerator(seed=seed).generate(...)`, so `VALIDSIM_LLM_ENABLED` and
> `VALIDSIM_LLM_API_KEY` currently have no effect on a validation run.
>
> The wider target pipeline — task description → LLM → scenario JSON →
> automated Isaac Sim scene edits — is also unimplemented; nothing performs
> scene edits. **12 categories:**

| # | Category | Example |
|---|---|---|
| 1 | Lighting changes | Intensity, color temp, direction, shadows |
| 2 | Object property changes | Mass, friction, deformability, size |
| 3 | Human proximity | Worker enters workspace, reaches near robot |
| 4 | Unexpected obstacles | New objects in workspace |
| 5 | Sensor degradation | Camera noise, occlusion, lens flare |
| 6 | Mechanical variation | Joint backlash, gripper wear |
| 7 | Environmental disturbance | Vibration, wind, temperature |
| 8 | Task ambiguity | Wrong object presented, partial occlusion |
| 9 | Multi-robot interference | Another robot in shared workspace |
| 10 | Emergency scenarios | Power loss, e-stop, network dropout |
| 11 | Adversarial inputs | Out-of-distribution objects, unusual poses |
| 12 | Temporal pressure | Speed increase, deadline constraints |

MVP target: **100 scenarios for bin picking** ([[8-Week Sprint Plan]] W4 exit criteria). Category #1 (lighting) and #2 (deformability) are pulled straight from the buyer's trauma in [[Problem Statement]] — night-shift lighting failure, broken gripper on deformable object.

> [!note] Category coverage is already guaranteed on the shipped path
> Because the rule-based generator cycles categories by index, **any `n >= 12`
> yields full coverage** (every category count `>= 1`); for `n < 12` the first
> `n` categories in tuple order appear. `ScenarioGenerator.coverage()` returns
> the per-category histogram. The LLM generator's top-up guarantee is a
> *different* mechanism for the same property, on a path no run takes.

## Module 4 · Evaluation & Scoring Engine *(Sprint W3, W5)*

| Metric | Calculation | Output |
|---|---|---|
| Success Rate | Completed episodes / Total episodes × 100% | Per-task, per-scenario, overall |
| Failure Taxonomy | Rule-based classification (LLM classification is a target) | Categorized failure list |
| Safety Score | Weighted composite of collision, force, proximity metrics | 0–100 score |
| Robustness Score | Std deviation of success rate across randomization variants | 0–100 score, or **unmeasured** on a normal run; see the note below |
| Regression Delta | Success(N) − Success(N−1) with CI | Per-task delta |
| Statistical Significance | Bootstrap resampling, 95% CI | p-value, confidence interval |
| **Composite Score** | **Weighted mean of the *measured* components: 40% success + 30% safety + 20% robustness + 10% regression** | **0–100** |

> [!warning] Two of the four terms are usually *unmeasured* — and now abstain
> Two components are not measurements in ordinary use:
>
> - **Robustness is unmeasured.** It is a dispersion *across randomization
>   groups*, and `run_validation` applies a single `task.randomization` level to
>   every episode — so there is exactly one group and nothing was varied.
>   Verified: a 5,000-episode run yields `randomization_group_count: 1`. The
>   scorecard reports `robustness_measured: false`.
> - **Regression is unmeasured with no baseline**, meaning nothing was compared.
>   Reported as `regression_baseline_available: false`.
>
> **Since 2026-09-29 an unmeasured component abstains**: its weight leaves the
> composite's denominator rather than contributing a fabricated `100`. Previously
> both scored 100 by construction, so **30 of the 100 points were awarded
> unconditionally** — a run where *every episode failed* (`success_rate = 0.0`)
> scored 60.0 and was **APPROVED at threshold 60**. It now scores **42.86 →
> BLOCK at any threshold**, while a flawless run still reaches 100.0.
>
> Trade-off: composites are comparable only across runs with the same evidence
> coverage, so **read the score alongside `robustness_measured` and
> `regression_baseline_available`.** See `docs/adr/0002` for the full rationale.
>
> Separately from the composite, a run is `BLOCK`ed if it under-delivered its
> requested episodes or recorded no success, and an adversarial segment of `>= 30`
> episodes is gated by a one-sided binomial test against a 60% success floor.

Composite drives [[Scorecard UX]] and the gate threshold (e.g. `--threshold 85`, [[CLI Design]]).

## Flywheel coupling

Every run feeds back: episode recordings → failure taxonomy training data → better scenario-generation prompts → more discriminating benchmarks. This compounding loop is moat #3 in [[Moat]] and advantage #7 in [[Strategic Advantages]]. **Target design**: today the only persisted artifact is the structured episode/scorecard JSON (no media, and no LLM prompt is generated from it), so the "better prompts" arrow does not yet exist in code.
