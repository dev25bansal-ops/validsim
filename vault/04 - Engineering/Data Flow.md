# 🔄 Data Flow (End-to-End)

The six-step lifecycle of one validation run through [[Solution Architecture]]. This is the script for the demo video ([[YC Countdown]]) and the sequence diagram for the blog post ([[8-Week Sprint Plan]] W8).

> [!important] Blueprint status — 2026-09-21
> Steps 1, 3, 4, 5 and history/delete are partly or fully shipped for the mock/HTTP-worker contract, but Steps 2 and 6 below are target-state. Kubernetes/Argo scheduling, S3/GCS HDF5+MP4 recording, TimescaleDB, generic webhooks, fleet deployment, and immutable/hash-chained audit logs are not implemented in this repository.

## Step 1: SUBMIT
```
Developer pushes model checkpoint to registry
→ Triggers GitHub Action / CLI command
→ POST /api/v1/validations {checkpoint, task_config, robot_spec, environment}
```
- Entry surfaces: `validsim run --checkpoint ./models/gr00t_v42.pt --task bin_picking ...` ([[CLI Design]]) or the Actions YAML ([[GitHub Actions Integration]])
- Payload validated by Pydantic v2 config parser ([[Module Specs]] M1)
- **Shared engine pipeline.** Every surface — the synchronous API (`POST /api/v1/validations`), the CLI (`validsim run`/`validate`), and the async job worker — executes the *same* `run_and_score` sequence (Steps 3–5 below), so the scorecard inputs can never drift between paths

## Step 2: QUEUE
```
Job enters Redis queue
→ Orchestrator assigns GPU resources (Kubernetes + Argo Workflows)
→ Isaac Sim container spins up with specified scene
```
- Planned priority/dead-letter handling and GPU scheduling are not implemented; the shipped queue is bounded FIFO memory/Redis.
- **Async job queue (shipped path).** `POST /api/v1/jobs` enqueues a `JobSpec` on a memory or Redis queue (`VALIDSIM_JOB_QUEUE`) and returns `202 {job_id}` immediately; a `JobWorker` later claims it and runs the *identical* `run_and_score` pipeline, persisting the result under the job's own `run_id` ([[Async Job Queue]], [[Job Queue Worker]])

## Step 3: SIMULATE
```
Parallel episode execution begins
→ 1,000–100,000 episodes across 8–64 GPUs
→ Domain randomization applied per episode
→ Adversarial scenarios injected (50–100 per run), generated by the
  deterministic rule-based generator
→ Episode data recorded: video, joint states, forces, contacts, timestamps
```
- Planned GPU envelope: 1,000–5,000 episodes, <30 min on 4× A100; this is a benchmark target, not a measured result ([[MVP Success Metrics]]). The shipped engine runs episodes **serially** in-process.
- **The `LLM-generated` step is not what runs.** Scenario generation on every
  shipped path is the deterministic rule-based generator; the LLM generator
  exists in `validsim/scenarios/llm_generator.py` but is never constructed by
  the pipeline, so this step is reproducible from `(checkpoint_id, task_id)` and
  makes no network call.
- **One randomization level per run.** `run_validation` passes
  `randomization_level=task.randomization` to every episode, so a run exercises a
  single domain-randomization condition. The consequence reaches the scorecard:
  `robustness_score` is a structural 100.0 on every ordinary run
  (`robustness_measured: false`, `randomization_group_count: 1`).
- HDF5 + MP4 recording to S3/GCS is planned; the current store persists structured episode result JSON, not media files

## Step 4: EVALUATE
```
All episodes complete
→ Success rate calculated per task, per scenario
→ Failure taxonomy classified (rule-based; LLM classification is a target)
→ Safety metrics computed (collisions, forces, proximity)
→ Regression delta computed vs. previous checkpoint
→ Statistical significance tested (bootstrap, 95% CI)
```
- Writes structured run/scorecard/episode results to the selected memory, SQLite or PostgreSQL 16 store; TimescaleDB is not configured
- Formulas and weights: [[Module Specs]] M4; example output: "Deformable grasp 89% → 84% (p=0.03)" ([[Scorecard UX]])

## Step 5: REPORT
```
Scorecard generated
→ Static FastAPI dashboard updated
→ PDF/JSON (and Markdown/HTML) reports available
→ A local Actions workflow can render a PR comment; generic webhook dispatch is a library capability, not a public registration API
→ Stored deployment decision: APPROVE ✅ or BLOCK ❌; current CI consumes it through `validsim gate`
```
- **Scorecard generation < 5 min post-simulation; dashboard loads < 2 s** — these
  are **targets, not measurements**. No benchmark in this repository measures
  either. What is verifiable: scorecard assembly is pure arithmetic plus a
  500-resample bootstrap, so it is CPU-cheap at any episode count the store
  accepts; the dashboard is static HTML/JS served by FastAPI.
- **Never derive a cost or duration figure from `EpisodeResult.duration_s` or
  `EvaluationResult.mean_duration_s`.** Both are **seeded RNG draws**
  (`validsim/sim/runner.py` draws `duration` from `rng.uniform(4.0, 12.0)` and
  friends), not measured wall-clock, and the two are algebraically identical
  (mean × N ≡ sum) — so the aggregate looks authoritative while being the same
  fiction. Reproduced at 5,000 episodes: sum ≈ 50,500 s ≈ 14 A100-hours ≈ **$49
  per run** at the $3.50/A100-hr rate in [[Unit Economics]], i.e. roughly **8×**
  the vault's $5–7 per 5K run claim, and stable to ±0.2% across seeds — which is
  exactly what makes it dangerous. See `docs/PLATFORM_PROPOSAL.md` §7.1.
- History is queryable by date range (`GET /api/v1/validations?since=…&until=…`, inclusive ISO-8601 bounds on `created_at`) and prunable (`DELETE /api/v1/validations/{run_id}` → `204`, or `validsim delete`), both backed by the store's `history(since, until)` / `delete()` ([[API Design]])

## Step 6: DEPLOY (or don't) — target state
```
If approved → checkpoint deployment may proceed
If blocked → CI/CLI reports failure details
→ A dedicated immutable audit record is retained
```

> [!important] The audit trail is the compounding asset — target design
> Every approved or blocked run is intended to append a hash-chained record for the insurer-facing product ([[Buyer Tiers]], [[Compliance]]), failure-taxonomy flywheel ([[Moat]]) and liability defense ([[Pain Quantified]]). It does not exist today: validation history is not hash-chained and the CLI/API support permanent deletion. Treat this as a build/company-policy decision, not a shipped moat.

## Async submission flow

The six steps above describe the *synchronous* run (API/CLI hold the connection through Steps 3–5). The async path decouples submission from execution while reusing the exact same engine pipeline:

```
POST /api/v1/jobs ─▶ JobSpec ─▶ enqueue (memory | Redis) ─▶ 202 {job_id}
                                                              │
                                                JobWorker.run_once()
                                                              ▼
                                  run_and_score  (Steps 3–5, identical)
                                                              ▼
                                  StoredRun persisted ─▶ JobRecord: queued→running→done|failed
                                                              │
                                  caller polls  GET /jobs/{id}[/status]  or streams /events (SSE)
```

- **Same pipeline, different transport.** The worker injects its own backend and the job's `run_id` into `run_and_score`, so the queue's `result` and the stored run share one key — no lookup table ([[Job Queue Worker]]).
- **Fire-and-forget.** Async submission returns `202`; the current worker can remove the long-run socket wait. The historical 15–45 minute simulation figure is a target, not a measured current run.
- **Bounded overload.** The queue caps at `max_depth` (default 1,000); a full queue returns `503` + `Retry-After` instead of growing without limit.

> [!note] Observability spans every step
> Each request is stamped with an `X-Request-ID` (reused if supplied, else a fresh `uuid4`) and echoed on the response; one structured JSON log line (method, path, status, duration_ms, request_id) is emitted per request, and a Prometheus scrape at `/metrics` exposes run/approval/block gauges plus HTTP-request counters by status class. The `/api/v1/health` probe reports the live store and queue backends ([[Tech Stack]], [[Module Specs]]).

## Latency budget (single run)

**Every row below is a target or a persona goal. None is a measurement**, and
nothing in this repository benchmarks them.

| Stage | Budget | Status |
|---|---|---|
| Submit → queue | seconds | target — unaudited; the enqueue is an in-memory append |
| Simulate (5,000 episodes) | 15–45 min (target <30 min, 4× A100) | target — **requires GPU/Isaac; the shipped engine is a serial CPU mock** |
| Evaluate + report | < 5 min | target — unaudited |
| Engineer's total wait | **< 1 hour** | persona goal, not an SLO ([[User Personas]]) |
